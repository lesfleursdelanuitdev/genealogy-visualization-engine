## API changes (steps 1–3; the full list for 0.1.0 is in CHANGELOG.md)

**Added:** `createGraphSnapshot`, `GraphSnapshot`, `GraphInput`, `SnapshotUnion`, `SpouseLink`, `EMPTY_GRAPH`, `unionIdOf`; `createChartSession`, `ChartSession`, `ChartSessionInit`, `ChartSessionOptions`, `ChartLayout`, `layoutChart`, `isGraphSnapshot`; `createTreeReducer`; `BuildTreeResult` exported; `useChartViewFetch` returns `graph`.

**Changed (breaking):**
- `buildTree(rootId, strategy, { graph, maxDepth, getHiddenCount })`: `graph` is required. `BuildContext` has `graph`; `people` is a `ReadonlyMap`.
- `treeReducer(state, action, graph?)`: without a graph, data-dependent actions do nothing.
- `countDescendants(graph, personId)`, cached per snapshot. `ViewStrategyDescriptor.getHiddenCount(graph, personId)`.
- `isAllSpousesRevealed(graph, revealedUnions, rootId?)`, `buildLegendItems(graph, …)`, `HandlePersonCardActionContext.graph` (required), `useDepth({ graph })` (was `builder`).
- `ChartViewBuildAdapter` has `graph` instead of `getDataBuilder()`.
- `main`/`types`/`exports` point at `dist/` (only `.` and `./package.json`; the `./*` → `src/*` subpath export is gone).
- Unions without an id get `husb-wife` everywhere (the catch-all used `""` before and treated them as revealed).

**Removed:** `FamilyTreeBuilder` (+ `FamilyTreeBuildOptions`, `FamilyTreeBuilderInput`), `setCurrentBuilder`, `clearCurrentBuilder`, `setCurrentTreeData`, `clearCurrentTreeData`, the eight global getters (`getPeople`, `getUnions`, `getUnionsByPerson`, `getAllChildrenOf`, `getParentUnionsByChild`, `getUnionById`, `getBirthUnionByChild`, `getSpousesOf`: use the graph's fields and methods), `clearDescendantCountCache`, `buildView`, `FamilyTreeNodeFactory` (+ config, descriptors), `useDescendancyFetch`, `getAllActionTypes`, `serializeNode`, test data (`buildTestTree`, `UNIONS`, `*_BY_*`, `PEOPLE_WITH_*`), and from the index only: `DescendancyChartAdapter`, `PedigreeChartBuilder`, `VerticalPedigreeChartBuilder`, `FanChartBuilder`, `PedigreeViewStrategy`.

**Of the 92 exports the app doesn't use**, the rest are kept as renderer/viewer API: layout, bounds and connector helpers, fan geometry, node classes and types, the strategy and layout option types, `UnionRecord`/`UnionChild`/`LinkedUnionEntry`, `CHART_VIEW_STRATEGIES`, `computeFitToViewport` and the hook option/result types. `DEFAULT_ROOT_XREF` stays until step 4 removes the default root.

**Gonsalves migration (step 6) will need:** `graph` from `useChartViewFetch` into `createTreeReducer`, `useDepth`, `handlePersonCardAction` and `buildLegendItems`; the global getters replaced by `graph.*` (18 imports across the app's files, counted by name); `isAllSpousesRevealed(graph, …)` (2 files).

## Decisions taken in this run

- **Extra dev dependencies:** `react-dom` 19.2.4 (must equal the locked `react` 19.2.4; the app has 19.2.3 of both), `jsdom` 30.1.3 (no install scripts) and `@types/react-dom` 19.2.3 (app's version), for the hook repros (H2, B01, B02, B07, B08, B14, B15, S3). No testing-library: a 60-line harness in `test/helpers/renderHook.ts`.
- **vitest 4.0.18** matches the app but `npm audit` flags it (GHSA-82fw-gwwq-j7x9 moderate, GHSA-qxg6-89mg-rqv8 critical; fixed in 4.1.11). Both concern vitest's mock/server API; we only run `vitest run`. The app has the same version.
- **`dist/` is bundler-only ESM:** the source's imports have no extensions, so `tsc` emits them as is. Fine for Vite, Next and vitest; bare Node ESM can't load it.
- **Test data** lives in `test/fixtures/smith`, outside the package. `test/boundaries.test.ts` fails if `src/` imports it, mentions a current builder, or has a module-level `let`/`var` outside `debug/`.
- **Sessions take `{ people, unions }` or a snapshot.** A session over 70,000 people should get the snapshot, built once per file, so a view-state change doesn't rebuild the indexes.
- **Not touched yet:** the `unknownPerson` "Unknown" placeholder rule, `isLiving` mapping, the default root, `process.env`, console logs: all belong to steps 4 and 5 and have repros.

## Steps 4–7 and T17–T31 (2026-10-30, second run)

**Decisions followed:** T17 vitest 4.1.12; T18 Show children in place; T19 CLOSE_SPOUSE `personId`; T20 one birth-family rule; T21 CHIL order; T22 dist bundler-only (README); T23 card actions wait (only `expandDown` changed, by T18); T30 "+N" on all charts; T31 phones. The living rule (T10) is not in the engine: it only treats a missing `isLiving` as living.

**Readings I chose (please confirm):**
- **T20, "the first FAMC listed in the file":** read as "the first family, in FAMC order, where the child's pedi is birth; else the first family". A file without PEDI (all birth) gets exactly the first FAMC. Taken literally ("first FAMC, whatever its pedi"), a child whose adoption is listed first would show the adoptive parents as birth parents. One-line change if the literal reading is wanted.
- **FAMC order** isn't in `DescendancyPerson`/`UnionRecord` (unchanged), so `GraphInput` gained an optional `famcOrder: Map<personId, familyIds[]>`. Without it, union (FAM record) order is used. **Step 2's converter should fill it** from each INDI's FAMC lines. That is an addition to the shared input shape, so it needs the step-2 colleague's agreement.
- **Placeholders:** the converter may send per-family placeholders as people (any id matching `:unknown-(husb|wife)` is flagged) or leave `husb`/`wife` empty; both work.
- **T30 field:** `_hiddenCount` is reused (documented in `types.ts`). A separate field didn't seem cleaner: each chart has one direction, and the renderer draws one chip.
- **T30 chip on Descendants** reuses T18 (`showChildrenOf`, "Show children"); on the ancestor charts it is `showParentsOf` with a "Show ancestors" entry. Tapping the chip on a collapsed descendancy branch opens one generation and keeps the branch collapsed beyond it.
- **Sibling view port:** with an unknown father it roots at the mother (the server rooted at the person); one-parent families count as a partner's other families; a duplicate FAM of the birth couple is not "other".

**History (coordinator's requirement):** `test/history.test.ts` walks a session through Show partner, Show children at the cap, Pan to person, Close partner, Pedigree view and Make root, then BACK ×3, FORWARD, NAVIGATE_TO_INDEX ×2, a branching action, CLEAR_HISTORY and RESTORE_HISTORY, checking labels, display names, strategyName per entry, MAX_HISTORY 21 and the built chart at each step. Entry-shape changes are in CHANGELOG ("History entries"). Old saved entries that reveal `""` keep working (08d9276).

**T31: what belongs to the renderer (step 3):**
- `user-select: none` on the chart (the hook no longer cancels pointerdown on interactive targets, so text selection must be stopped by CSS);
- card buttons as real `<button>` (or `[data-chart-interactive]`) so presses on them stay taps, with no `stopPropagation` on their pointerdown (or a pan can't start there);
- no re-mounting of card DOM when `dragging` toggles (a re-mounted button loses its click);
- drop `onWheel` from the `<svg>`; pass `viewKey`;
- 44 px targets and `touch-action: manipulation` on toolbar controls outside the `<svg>` (no double-tap zoom);
- real-device checks (Playwright phone emulation in step 4): jsdom has no native scrolling, inertia or iOS gesture events, so "nothing leaks" is tested here only as touch-action plus cancelled events.

**Server-logic port (feb9eb9):** `src/graph/queries.ts`, 227 lines (157 of code) plus 137 lines of tests, close to the inventory's ~245 estimate.

**Performance:** 10,239 people with heavy pedigree collapse, a capped pedigree with "+N" counts builds in about 140 ms and a capped descendancy in about 20 ms, snapshot included (test budget 1 s).

**Not done here, by design:** tagging (waits for momolig); the 8 TBD card actions (T23); the Gonsalves migration (step 6 of the order of work); `applyPrivacy` (renderer).
